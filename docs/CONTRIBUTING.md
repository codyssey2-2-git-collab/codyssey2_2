# Contributing Guide

## 브랜치 전략(GitHub Flow)

이 프로젝트는 복잡한 기능 구현이나 실시간 서비스 배포가 아닌, 협업 환경을 조성하고 연습하는 것을 목적으로 하므로 다음과 같이 단순한 규칙을 사용한다.

- **GitHub Flow 사용:** 관리의 복잡성을 줄이기 위해, 코드든 문서든 새로운 변경 사항을 추가하는 모든 독립된 작업은 `feature/` 브랜치 하나로 통일한다. 브랜치는 다음 두 종류만 사용한다.

  - `main`: 검토가 끝난 작업만 적용되는 브랜치. `feature/*` 브랜치에서 PR을 생성하고, 코드 리뷰를 거쳐 리뷰어 **최소 1명의 승인**을 받아 이상이 없음을 확인한 뒤 merge해야하며, 직접 push하지 않는다.(저장소 설정의 Branch protection으로 강제한다.)
  
  - `feature/*`: 작업 단위 브랜치

## 브랜치 네이밍 규칙

팀 저장소의 브랜치 이름 규칙을 정의한다.

- **이슈 번호 생략:** 외부 PM 도구(Jira 등)나 CI/CD 툴을 연동하지 않고 기본적인 충돌 해결과 이슈 관리 방법을 익히는 것으로 충분하므로, 브랜치명에 이슈 번호를 넣지 않는다. 이슈와 작업의 연결은 PR 본문에 `Closes #12`와 같이 작성하여 관리한다. (PR이 merge되면 이슈가 자동으로 닫힌다.)
  
- **작성자 표기:** 누가 어떤 작업을 진행 중인지 브랜치 목록만으로 추적할 수 있도록, 브랜치명에 작성자 ID를 넣는다.

아래 규칙은 Git/GitHub에서 **아예 생성이 불가능한 이름**과, 생성은 되지만 **협업 중 문제를 일으키는 이름**을 모두 피하는 것을 목적으로 한다.

---

### 기본 형식

```
feature/<작성자>-<짧은-설명>
```

| 예시 | 설명 |
|---|---|
| `feature/alice-add-branch-naming-rule` | 브랜치 네이밍 규칙 추가 |
| `feature/bob-update-readme` | README 수정 |

---

### 작성 규칙

- 버그 수정, 문서, 리팩터링 등 **모든 작업 브랜치는 `feature/`로 시작**한다.
  
- `<작성자>`는 팀원별로 정한 **영문 소문자 ID**를 쓴다. ID에는 하이픈(`-`)을 넣지 않는다.
  
- **소문자 영문, 숫자, 하이픈(`-`)만 사용**한다. 구분자 `/`는 `feature` 뒤에 **한 번만** 쓴다.
  
- 단어 구분은 하이픈(`-`)으로 한다. 언더스코어(`_`), 공백, camelCase는 쓰지 않는다.
  
- 설명은 영어 2~5단어로 짧게 쓴다. (작성자 ID는 단어 수에 포함하지 않는다.) 전체 길이는 **50자 이내**를 권장
  
- **`feature`라는 이름만으로 된 브랜치는 만들지 않는다.**
  → `feature` 브랜치가 존재하면 `feature/...` 브랜치를 아무도 만들 수 없게 됨(1.3.3 참고)

- `main`, `HEAD` 등 예약·보호된 이름과 같거나 비슷한 이름을 쓰지 않는다.

---

### 금지 사항

#### Git이 생성을 거부하는 이름

| 금지 | 예시 | 이유 |
|---|---|---|
| 공백, 제어문자 | `feature login` | 셸 인자 분리와 충돌 |
| `~` `^` `:` | `fix~1`, `a:b` | 리비전 문법(`HEAD~1`, `HEAD^`, refspec)과 충돌 |
| `?` `*` `[` | `feat*` | glob 패턴과 충돌 |
| `\` | `feat\login` | 금지 문자 |
| `..` (연속 점) | `v1..2` | 범위 문법(`A..B`)과 충돌 |
| `@{` 포함, 단독 `@` | `x@{1}`, `@` | reflog 문법, `HEAD` 별칭과 충돌 |
| `/`로 시작·끝, `//` 연속 | `/feat`, `feat/`, `a//b` | 빈 경로 구성 요소 |
| 구성 요소가 `.`으로 시작 | `.hidden`, `feat/.x` | 금지 규칙 |
| `.`으로 끝남 | `feat.` | 금지 규칙 |
| 구성 요소가 `.lock`으로 끝남 | `main.lock` | Git 내부 잠금 파일과 충돌 |
| `-`로 시작 | `-feat` | 명령어 옵션으로 해석됨 |
| `HEAD` | `HEAD` | 특수 ref |

#### GitHub가 push를 거부하는 이름

- **40자리 16진수로만 된 이름** (예: `6733c897c319018fd0753caf8d4f8eb1fa35d75e`)
  - 커밋 해시와 구분할 수 없어 보안 문제가 생기므로 GitHub가 거부한다 (`GH002` 에러).
- 저장소에 Rulesets / Branch protection이 설정되어 있으면 그 패턴도 따라야 함

#### 생성은 되지만 협업 중 깨지는 이름

| 문제 | 예시 | 증상 |
|---|---|---|
| **계층 충돌** | `feature`와 `feature/login` 동시 존재 | ref가 파일/디렉터리로 저장되므로 둘 중 하나를 만들 수 없음 (`cannot create 'refs/heads/feature/login'`) |
| **대소문자만 다른 이름** | `Feature/x`와 `feature/x` | Linux·GitHub에선 별개지만 macOS·Windows에선 같은 파일로 취급되어 덮어쓰기·fetch 오류 |
| **너무 긴 이름** | 255바이트 초과 | 파일 생성 실패, Windows에선 경로 260자 제한에 걸림 |
| **비ASCII 문자** | `feature/로그인`, 이모지 | 인코딩, CI 스크립트, URL 처리에서 깨짐 |
| **셸 특수문자** | `!` `$` `&` `#` `'` `"` | 스크립트에서 따옴표·이스케이프 누락 시 오동작 |

---

### 확인 방법

브랜치를 만들기 전에 Git 규칙에 맞는지 확인할 수 있다.

```bash
git check-ref-format --branch "feature/alice-add-branch-naming-rule"
# 유효하면 이름이 출력되고, 아니면 에러
```

> 이 명령은 1.3.1의 Git 규칙만 검사한다. 팀 규칙(1.1~1.2)까지 검사하려면 훅을 사용

---

### 브랜치 이름을 잘못 만들었을 때

```bash
# 로컬 브랜치 이름 변경
git branch -m <잘못된-이름> <올바른-이름>

# 이미 push했다면: 새 이름으로 push 후 원격의 옛 브랜치 삭제
git push -u origin <올바른-이름>
git push origin --delete <잘못된-이름>
```

> 열려 있는 PR이 있다면, 원격 브랜치를 삭제하기 전에 GitHub에서 PR의 브랜치를 먼저 확인해야함

## 커밋 메시지 컨벤션

형식: `<종류>: <구체적인 변경 내용>`

종류 표시 뒤의 설명은 한국어로 쓰고 `~했음`으로 끝낸다. 메시지만 보고 무엇을 바꿨는지 알 수 있도록 변경 대상을 구체적으로 적는다.

| 종류 | 사용 시점 |
| --- | --- |
| `feat` | 기능 또는 학습 결과물을 추가했을 때 |
| `fix` | 오류를 수정했을 때 |
| `docs` | 문서를 추가하거나 수정했을 때 |
| `refactor` | 동작은 유지하면서 코드 구조를 개선했을 때 |
| `test` | 테스트를 추가하거나 수정했을 때 |
| `chore` | 설정이나 저장소 관리 작업을 했을 때 |

좋은 예:

- `docs: PR 작성 규칙 정리했음`
- `feat: 브랜치 개념 학습 노트 추가했음`
- `fix: 예시 명령어의 오타 수정했음`

금지하는 예: `update`, `fix`, `wip`, `final`, `bug fix`, `edit file`처럼 변경 대상과 내용을 알 수 없는 메시지.

## PR 작성 규칙

PR 제목은 변경 내용을 알 수 있도록 한국어로 구체적으로 적는다. PR 본문에는 다음 항목을 모두 포함한다.

1. **연결 Issue:** `Closes #이슈번호` 또는 `Fixes #이슈번호`
2. **변경 사항(What):** 무엇을 변경했는지
3. **변경 이유(Why):** 왜 변경했는지
4. **테스트·검증 방법(How):** 무엇을 확인했고 결과가 어땠는지

수행하지 못한 검증이 있다면 그 이유를 본문에 적는다.

PR을 작성할 때 [PR 본문 템플릿](../.github/PULL_REQUEST_TEMPLATE.md)을 참고한다.
